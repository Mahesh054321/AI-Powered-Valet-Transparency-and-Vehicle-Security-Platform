# Demonstration data

Everything in this document describes **synthetic** data. No row in the demo
dataset is a record of a real valet operation, and no model in this project is
trained on real customer data.

---

## 1. Reset and reseed in one command

```bash
cd backend
python utils/scripts/seed_demo.py            # reset + curated seed + 90 days of history
python utils/scripts/seed_demo.py --days 30  # shorter history, faster
python utils/scripts/seed_demo.py --no-history   # curated rows only
python utils/scripts/seed_demo.py --keep     # top up without dropping tables
python utils/scripts/seed_demo.py --seed 7   # a different-but-equally-plausible history
```

The script drops every table and trigger function, re-applies migrations
`0001`–`0008`, writes the curated demo rows, generates the operational history,
then **re-reads the database and verifies what it produced**. Verification
checks provenance labels from the rows themselves rather than trusting the code
that wrote them, and a failed check exits non-zero.

> `--reset` used to fail on a second run: migrations install trigger functions
> with a plain `CREATE FUNCTION`, and dropping tables left the functions
> behind, so re-migrating died on *"function already exists"*. `reset_database`
> now drops application-owned functions too, excluding extension-owned ones
> (pgcrypto) via `pg_depend`.

The layers can still be run individually if you want finer control:

```bash
python utils/scripts/init_db.py --reset --seed        # schema + curated rows
python utils/scripts/generate_operational_history.py --days 90 --reset
python utils/scripts/generate_retrieval_history.py    # writes JSON for model training
```

## 2. What the seed creates

### Curated layer — small, hand-built, always present

Written by `backend/database/seed.py`. Deterministic IDs (UUID5 over a fixed
namespace), so re-running creates nothing twice.

| Item | Count | Detail |
| --- | --- | --- |
| Customers | **3** | `customer.aisha@`, `customer.rohit@`, `customer.meera@example.com` |
| Vehicles | **4** | Aisha owns two (one in custody, one registered); Rohit and Meera one each |
| Valet operators | **2** | `valet.suresh@`, `valet.priya@example.com` |
| Manager | **1** | `manager.karan@example.com` |
| Parking zones | **3** | ZONE-A (40 bays), ZONE-B (60), ZONE-C (25, `MAINTENANCE`) |
| Custody sessions | **3** | one `PARKED`, one `CHECKED_OUT`, one `READY_FOR_PICKUP` |
| GPS fixes | **32** | all `SIMULATED`; 28 NORMAL, 2 WARNING, 2 BREACH |
| Inspections | **6** | drop-off + pickup for each session |
| Damage findings | **9** | method `CLASSICAL_CV`, each with reasoning and parameters |
| Security alerts | **1** | geofence breach, `HIGH`, acknowledged |
| Retrieval predictions | **2** | heuristic queue model, confidence 0.71 |

Three custody states are covered deliberately, so every dashboard has something
to show: a car still parked, a car on its way back, and a closed job with new
damage found at pickup.

### Generated layer — bulk history, optional

Written by `backend/utils/scripts/generate_operational_history.py`. At the
default 90 days this adds roughly 1,100 tickets and custody sessions, ~2,200
inspections, ~50 security alerts, ~1,100 retrieval predictions and ~12,000 GPS
fixes, spread with weekday seasonality and queue pressure by hour of day.

Without it the manager dashboard charts two points, which is not a trend.

## 3. Movement samples

GPS fixes are generated by `ai/synthetic/gps_tracks.py` and every verdict is
computed by the same `ai/anomaly/geofence.evaluate_fix` the live API uses,
against the zone's **real polygon**. Nothing is a hand-written status: if the
engine's thresholds change, the seeded statuses change with them.

| Scenario | Used for | Verdicts produced |
| --- | --- | --- |
| `parked` | routine custody | `NORMAL` |
| `jitter` | GPS noise near the boundary | `NORMAL`, `WARNING` |
| `telemetry_loss` | tracker goes quiet | `NORMAL`, `WARNING` |
| `unauthorised` | the suspicious sample | `SUSPICIOUS`, `BREACH` |

`arrival` and `retrieval` are deliberately **not** used for routine history.
Both legitimately drive the vehicle out of the yard, and the distance ladder
correctly reports `BREACH` for a fix 300 m outside the ring even though the
movement is authorised (`movement_expected` gates only the unauthorised-movement
rule, not the distance ladder). Seeding those against ordinary jobs would
scatter red breaches across routine work — the false positive that teaches
people to ignore a dashboard. Both remain available live via
`POST /api/v1/gps/simulate`.

Alerts and telemetry are correlated: a generated session is decided to be
suspicious *first*, then the `unauthorised` track is written and the alert is
attached to the specific fix that triggered it. In a 30-day run, 16 alerts were
generated and all 16 carried a `gps_event_id` pointing at a real row.

## 4. How synthetic data is labelled

| What | Where the label lives |
| --- | --- |
| GPS fixes | `gps_events.source = 'SIMULATED'` **per row**, plus a `SIM-*` device id. Provenance is stored per row rather than inferred from a setting, so one hardware tracker can be added later without relabelling anything. |
| Generated tickets / sessions | `metadata = {"is_demo": true, "origin": "operational_history"}` |
| Generated customers / vehicles | `notes` begins `[DEMO]` |
| Damage findings | `method = 'CLASSICAL_CV'`, with `reasoning` and `parameters`. No finding claims a trained model. |
| Retrieval predictions | `inputs_snapshot.history_is_synthetic = true`, `method = 'heuristic-queue-v1'`, `model_version = NULL`, and the explanation says so in prose. |
| Retrieval training data | `storage/data/retrieval_history.json` carries `source` and `disclaimer` keys. |
| API responses | `telemetry_source` is surfaced on telemetry payloads and on `/api/health`. |

`tests/test_demo_seed.py` asserts these from the database — including that zero
rows claim `HARDWARE` provenance and that no alert cites a GPS fix that does
not exist.

## 5. About "demo mode"

There is **no global demo flag**, and that is deliberate.

A flag that relaxes validation, widens a permission or lowers a detection
threshold for the sake of a demonstration would compromise normal
functionality — the exact thing the brief rules out. Instead, demo behaviour is
ordinary behaviour on synthetic inputs:

- `GET /api/v1/inspections/demo/scenarios` — list the synthetic photo scenarios
- `POST /api/v1/inspections/demo` — run the **real** `compare_images` pipeline
  over synthesised photos. The images are synthetic and the response says so;
  the findings are not canned and no threshold is bypassed.
- `GET /api/v1/gps/simulate/scenarios` — list the track scenarios
- `POST /api/v1/gps/simulate` — generate a track and ingest it as `SIMULATED`

All four are staff-authenticated and opt-in **per request**. Nothing about a
normal request changes because a demo endpoint exists, and seeded demo rows are
indistinguishable from real ones to the API — which is the point: the demo
exercises the production code path.

`TELEMETRY_SOURCE` (default `simulated`) is a deployment setting that labels
provenance; it does not alter behaviour.

## 6. Sign-in accounts

All seeded accounts share the password `Demo#Passw0rd`. It is an openly
documented demonstration credential, not a secret, and never a production
default — the real administrator password comes from `SEED_ADMIN_PASSWORD`.

| Email | Role |
| --- | --- |
| `admin@valet.local` | `ADMIN` |
| `manager.karan@example.com` | `VALET_MANAGER` |
| `valet.suresh@example.com` | `VALET_OPERATOR` |
| `valet.priya@example.com` | `VALET_OPERATOR` |
| `customer.aisha@example.com` | `CUSTOMER` |
| `customer.rohit@example.com` | `CUSTOMER` |
| `customer.meera@example.com` | `CUSTOMER` |

The history generator adds ~40 further customer accounts (`demo.*@example.com`)
purely to give the charts spread. They are not intended for sign-in.

Public registration can never produce an `ADMIN` or staff account; that is
enforced in the auth service and covered by tests.

## 7. Honest limitations

- Damage detection is a classical OpenCV pipeline, not a production-grade
  model. Uncertain findings are labelled *Potential Damage* and require manual
  verification.
- The security classifier and retrieval predictor are prototypes fitted on
  their own synthetic generators. Reported metrics describe performance on
  synthetic data only and say nothing about real-world accuracy.
- Generated history is plausible, not calibrated. It exists so charts have
  enough points to be read, not to represent any real operation.
